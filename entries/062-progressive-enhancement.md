# 062 — Progressive enhancement

> Entry 062 — added 2026-11-14 (Drop 6: Structure, comfort, and trust).

*The core works with nothing fancy attached, and every fancier layer is a bonus, not a requirement.*

**What it is.** Progressive enhancement means building in layers. The core works with the most basic, most resilient layer alone, and each fancier layer enhances it without being required for it. On a desktop app the layers are not HTML, CSS, and JavaScript. They are the local core (files on disk, CPU compute, plain widgets), then the enhancement layers: the GPU render path, the local model server, the network sync, the plugins. The rule is the same at every layer: if the layer is missing, slow, or broken, the app still does its core job, slower or plainer, but never dead. The idea comes from the web, where GOV.UK made it mandatory for all government services: HTML first, because the HTML layer is fault-tolerant by design and the browser ignores markup it does not understand; CSS next, reasonably fault-tolerant; JavaScript last, because JavaScript is not fault-tolerant at all and one unsupported call kills the whole script. The desktop translation is the content of this entry. The web layers are the origin story.

**Why it matters.** A system should not break wholly if a single part fails. That is the GOV.UK technical architect's own framing: progressive enhancement is about resilience as much as it is about inclusiveness. On Joshua's machine the fancy layer is missing more often than it is present: no GPU, WiFi only, Ollama sometimes down, no model pulled yet. An app that needs its enhancement layer to open is an app that is broken on the machine it was built for. The same logic covers failure, not just absence. A layer can fail for reasons nobody predicted, a driver update, a proxy, a stalled download, and the user never chose any of it. GOV.UK's research found in 2016 that 0.9% of its visits came from people without JavaScript available who had not chosen to turn it off. The core service still worked for them, because the core never needed the script layer. Build the core first and the app is robust on every machine it meets, including this one.

**The key facts.** The web layers set the pattern. HTML is fault-tolerant by design, CSS ignores declarations it does not understand, and JavaScript fails whole: one unsupported call stops the rest of the script running. GOV.UK's rule follows from that: JavaScript should only enhance HTML and CSS that already provide the same core function, an autocomplete enhancing a select element, so the user can still do the job when the script fails. The desktop proof is Blender. Its Cycles renderer can use either the CPU or certain GPUs, and when the render device is set to None, or when None is the only option, the CPU is used as the computing device. The manual states the UI rule too: if the hardware does not support an option, it will either not be displayed or be corrected on startup. The CPU path is not a crippled fallback. GPU rendering is faster, but GPUs have limited memory, and the manual's own FAQ asks why a scene that renders on the CPU does not render on the GPU: the most common cause is that the graphics card ran out of memory, while the CPU can use the much larger system memory. The boundary is honest too. Blender's realtime engine Eevee only uses the GPU to render, with no plan to support CPU rendering, so not every layer degrades, and the app says so. Google Sheets shows the same pattern on the web: without JavaScript it shows a non-editable view of the data, curtailed but present, and the document still exists.

**Where it fits his apps.** Fyrn: the library, model management, and the pull queue work when Ollama is down or no model is pulled; chat is the enhancement, not the app. STELLA: training runs with plain CPU settings when the GPU path is absent, and the profile, the data, and the results stay usable throughout. ACR: analysis runs without a model loaded, with the local model as enhancement for embeddings, so the trace and the numbers never depend on a server being up. Pixel Forge: editing works on the CPU preview path when GPU-accelerated previews are unavailable, slower but fully functional. MIMIK: capture and local playback need no network at all; sharing and sync are enhancements that arrive when the connection does. GITDATA: the local index browses and searches offline, and remote sync adds to it rather than gating it. Qwkhnd: tasks and triage are fully local, and anything that syncs is a layer on top. In Qt the Blender rule applies directly: detect the layer at startup and hide or correct what needs it, never show a control that cannot work. A dialog that grows a section when a layer appears must scroll, and a focus ring that never appears is a broken promise, so focus rings are a border on :focus, since outline renders 0 pixels in this build.

**What it gets wrong.** The core must be genuinely usable, not a stub with a smile. A read-only view, like Sheets without JavaScript, is a compromise the user can accept; a spinner that never resolves is not progressive enhancement, it is the same dead screen with better manners. The enhancement must never quietly become required: if the app only ever gets tested with every layer on, the core rots unnoticed, so test with the layer off, the way GOV.UK tests on older and lower-powered devices. Extra layers have costs of their own. GOV.UK warns that client-side frameworks increase code size, push processing onto the user, and create reliance on third-party code, and its verdict on single-page applications is blunt: do not build your service as one, because a single failed script takes the whole service with it. And not everything degrades. Eevee is GPU-only by design, and pretending otherwise would be dishonest; when a layer genuinely cannot be replaced, say so plainly in the UI and keep everything else working around it.
